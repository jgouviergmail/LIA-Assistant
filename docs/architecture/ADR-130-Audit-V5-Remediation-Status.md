## Context and Problem Statement

L'audit V5 a émis 11 findings à traiter (9 Partiels déjà partiellement adressés par des passes antérieures, 2 Nouveaux). La contrainte de travail était : remédiation **INLINE** (pas de délégation à des sous-agents), **zéro régression** comme priorité #1, et — pour tout ce qui touche du code existant — une preuve exécutable plutôt qu'une confiance dans la revue.

Ce document est un **ADR de bilan** : il n'introduit pas une nouvelle architecture mais **acte l'état de la remédiation** (fait / en cours / restant), les **décisions de séquençage et d'arbitrage** prises en cours de route, et la **gouvernance par ratchets** qui verrouille les gains. Il s'appuie sur les ADR déjà émis pour les deux chantiers majeurs (T1 → ADR-127, F001 → ADR-129) sans les dupliquer.

## Decision

### D1 — Méthodologie transverse

- **Décompositions caractérisation-first** : tout refactor d'un point chaud (F015, à venir F011) commence par des *golden/characterization tests* qui épinglent le comportement **actuel** et passent sur le code inchangé ; l'extraction est ensuite prouvée behavior-preserving en re-jouant ces mêmes tests à l'identique.
- **Gouvernance par ratchets shrink-only** (CI-enforced) : complexité backend (`measure_cc.py`), complexité frontend (`check-cc-ratchet.mjs`), dette d'exemptions mypy (`measure_mypy_debt.py`), cycles de couplage runtime (`measure_coupling.py`), taille des fichiers (`measure_sloc.py`). Chaque baseline ne peut que **baisser** ; une régression ou un nouveau contrevenant casse la CI.
- **Aucune action git** dans le cadre de ces passes (l'arbre reste non commité, l'humain gère git).

### D3 — Décisions d'arbitrage et de séquençage

- **F009 acté low-ROI** : les 31 cycles runtime restants sont dominés par le hub `users` ; les casser proprement (ports/DI) toucherait des chemins critiques pour un gain runtime faible. Décision : **conserver le ratchet** (empêche toute nouvelle régression) sans campagne de réduction dédiée pour l'instant.
- **Pause assumée sur les gros chantiers** : F001 Phase 2/3, la suite de F015 (347 hotspots, dont la jauge `max` = `_stream_with_new_services` CC 89 sur le chemin SSE/HITL, le plus risqué), et le reliquat F020 (91 paires, majorité **framework-légitime** = pattern TypedDict LangGraph où forcer le type imposerait un `cast` interdit) demandent chacun une **session dédiée** (brainstorm/spec/plan pour les greenfield, caractérisation lourde pour les hotspots risqués). Ils ne sont **pas** poursuivis dans l'immédiat.
- **Candidats de reprise à faible risque — RÉALISÉS (même jour)** : **F008** clôturé (suite Pester 25 tests, cf. tableau ; bootstrap Pester ≥ 5.5 en scope CurrentUser) et **F011** entamé sur sa priorité n°1 (le drift lockfile `vite@7`/`plugin-react@6` du conteneur a d'abord été réparé — sync host→conteneur puis `pnpm install --frozen-lockfile` — rendant le filet vitest exécutable : 773 tests verts).

### D4 — Qualité de test (transverse)

Un défaut d'**isolation de test** exposé par la suite complète a été corrigé dans la même passe : `RoutingDecider` est un singleton module-level ; `test_get_routing_decider_with_custom_thresholds` l'initialisait avec un seuil non-défaut sans le réinitialiser, polluant de façon **déterministe** (ordre de collecte `tests/unit` avant `tests/agents`) `test_decide_high_semantic_score`. Correction en deux couches : le test mutateur nettoie après lui (`teardown`) et le test victime réinitialise le singleton avant/après (order-independence).
