# Position place details and routes

Approved in chat: selecting a Position map marker shows the already acquired place information and computes a route on the same map, starting at current browser position, then an opted-in fresh last-known position, then home. No additional Places or LLM request is required for place details. Existing badge and compact-map fixes and all concurrent changes must be preserved. No commit, push or deployment is authorized.

## Tasks

1. Extend the bounded display projection and frontend parser with optional place details (address, rating and review count, phone, website, weekday opening hours). Read old archives. Reuse existing field normalization and safe URLs. Add behavioral projection/parser tests before implementation.
2. Add an authenticated, rate-limited `POST /connectors/google-maps/place-route` seam. Input: destination `{lat,lng}`, optional browser origin `{lat,lon,accuracy,timestamp}`; output: `origin_source`, `origin_as_of`, `travel_mode`, `polyline`, `distance_meters`, `duration_seconds`. Reuse the implicit-location cascade, Routes client, platform and user spend gates, and durable TrackingContext accounting. Close the client and release database reads before network work. Test refusal, fallback, failure/accounting, and output contracts.
3. Add one InfoWindow and one removable route polyline to the existing map controller. On marker/list selection, show a React-rendered detail panel and calculate only the selected route through a typed hook. Read browser position only under the existing application opt-in and granted browser permission. Cancel superseded requests, isolate by owner, retain bounded short-lived route results, clear the previous route immediately, and preserve focus and readable details on failure. Add translations in all six locales without replacing concurrent locale edits.
4. Validate targeted backend/frontend behavior, clean types, lint and i18n parity. Extend the hermetic responsive browser scenario for details, displayed route, missing origin, failure/retry, rapid selection and keyboard access. Run the broad repository gates with bounded worker counts and a Docker proof build. Record any inherited failures separately. Obtain an independent final review.

## Integration contracts

- Browser coordinates are optional; the server remains authoritative for account, last-known opt-in/freshness and home fallback. Home coordinates never enter archived place HTML.
- A route response has non-negative finite integer measurements and a bounded encoded polyline; no provider tree leaves the service.
- The map SDK controller owns its InfoWindow and route overlay and destroys both. React owns the details DOM; no unsanitized HTML injection.
- Clicking a different place never displays a late result for a previous place. Cache lifetime is bounded; repeated selection of the same origin/destination avoids another paid call.
- Details are limited to already received facts; absent fields stay absent. No new dependency is planned.
