# LIA v1.47.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a truthful, six-language, self-host-installable and verified LIA v1.47.1 from the approved staged implementation.

**Architecture:** Keep the already staged implementation in the current checkout and derive all release claims from code, tests and source documentation. Use the project's mechanical version script for version surfaces, edit human-facing copy explicitly, then validate the installer, CI gates and production in that order. Do not create a clean worktree: the approved 221-file index is the release candidate, and a new worktree would omit it.

**Tech Stack:** Python 3.14/FastAPI, Next.js 16/TypeScript, six JSON locales, Markdown, Taskfile, Docker Compose, PowerShell deployment.

**Spec:** `docs/superpowers/specs/2026-09-22-v1-47-1-release-design.md`

## Global Constraints

- The release version is exactly `1.47.1`; the tag is `v1.47.1`.
- Preserve the pre-existing staged 221 files and their content unless a verified defect requires a focused correction.
- No unsupported certification or blanket GDPR/EU AI Act compliance claim; the published 8.3/10 technical audit excludes security.
- Every user-facing addition ships in `en`, `fr`, `de`, `es`, `it`, `zh`; Story, Why and How are presentations, not changelogs.
- Do not weaken test/coverage/complexity baselines, skip hooks, or tag before installer and production proof.
- User authorized autonomous completion, commit, push, production deployment and release on `main`.

### Task 1: Audit candidate and measured facts

**Files:** Review `git diff --cached`, `apps/web/src/components/landing/constants.ts`, `README.md`, `CHANGELOG.md`, FAQ locale keys, `docs/architecture/ADR-302-*`, `scripts/install/`, Compose and release scripts. Produce evidence in the ensuing changes; no standalone inventory file is necessary.

**Interfaces:** Produces a release fact map (feature → implementation/test → public explanation), source-backed metric values and installer deltas for Tasks 2–4.

- [ ] **Step 1: Verify the candidate tree.** Run `git status --short --branch`, `git diff --cached --stat`, `git diff --check`, and `git log -1 --oneline`.
- [ ] **Step 2: Build feature and fix inventory.** Inspect staged code, tests, ADRs and existing guides. Distinguish end-user/admin changes from internal correctness changes.
- [ ] **Step 3: Re-measure public numbers.** Follow each `LANDING_STATS` source comment and compare with README, six guides, FAQ, blog and `llms.txt`.
- [ ] **Step 4: Classify installability impact.** Diff configuration, migrations, Compose, seeds and boot against `v1.47.0`; map actual deltas to installer files.

### Task 2: Release mechanics and documentation

**Files:** Modify version surfaces via `scripts/release/bump_surfaces.py`; edit `CHANGELOG.md`, `README.md`, affected `docs/`, and `apps/web/src/components/landing/constants.ts` when its numbers change. Test via release/docs gates.

**Interfaces:** Produces consistent version and factual documentation for the localized content in Task 3.

- [ ] **Step 1: Run release bump.** Execute `task release:bump -- 1.47.1`; inspect every changed path.
- [ ] **Step 2: Draft release note.** Add `1.47.1` to `CHANGELOG.md` from the feature/fix inventory, linking relevant ADRs and distinguishing user impact from internal fixes.
- [ ] **Step 3: Refresh README and docs.** Update feature descriptions and measured metrics; revise only directly/indirectly affected guides, knowledge files, technical docs and indexes. Update `CLAUDE.md` and regenerate `AGENTS.md` only if project instructions change.
- [ ] **Step 4: Verify documentation.** Run `task release:check`, `task lint:docs:preview` and `git diff --check`; resolve source drift, not only broken links.

### Task 3: Six-language public and application content

**Files:** Modify `apps/web/locales/{en,fr,de,es,it,zh}/translation.json`, `apps/web/src/data/guides/{story,why,how}.*.md`, `apps/web/src/data/blog-articles.ts`, landing/FAQ/changelog components and tests only where content or wiring requires it, and affected `docs/knowledge/`.

**Interfaces:** Produces the localized FAQ, searchable settings terms, landing and changelog content that Task 5 verifies in the browser.

- [ ] **Step 1: Add application FAQ and release changelog copy.** Include only user/admin-facing changes, preserve numbering and `CHANGELOG_VERSION_KEYS` wiring, balance touched “How LIA works” answers.
- [ ] **Step 2: Explain capabilities across public pages.** Update home, Philosophy, Technical, Story, More, public FAQ, existing relevant blog articles, New and history with durable messaging; no gratuitous animation. Keep date/time truthful.
- [ ] **Step 3: Update all six locales and knowledge.** Translate every new key, audit settings search lexicon, synchronize affected FAQ-derived knowledge files.
- [ ] **Step 4: Verify frontend content.** Run `task lint:i18n`, affected Vitest tests, `task lint:frontend`, and `pnpm exec tsc --noEmit --incremental false` from `apps/web`.

### Task 4: Fresh-install contract

**Files:** Modify `scripts/install/{envgen,questions,compose,deploy}.py`, `.env.min.prod.example`, their tests, and `docs/GETTING_STARTED.md` only for real deltas found in Task 1.

**Interfaces:** Produces a release that can be installed from zero with current defaults and migrations.

- [ ] **Step 1: Write failing installer/Settings contract tests if a delta exists.** Pin the exact new requirement to the wizard's rendered defaults, optional question, service profile, seed or boot sequence.
- [ ] **Step 2: Make the minimal installer/documentation change and re-run the focused test.** Do not introduce a mandatory setting for an optional provider.
- [ ] **Step 3: Run `task test:install` and the backend defaults-to-`Settings` guard.** Both must be green before tag.
- [ ] **Step 4: Run `task test:install:hermetic` and `task release:check`.** Inspect test counts and warnings.

### Task 5: Full quality and publication

**Files:** Edit only files implicated by concrete failing gates; stage/review release delta before commit.

**Interfaces:** Produces the pushed commit, verified production and release tag.

- [ ] **Step 1: Run targeted behavior/integration/browser tests, `task ci:fast`, and `task ci` where runtime changes warrant it.** Correct errors/warnings without weakening gates; rerun the complete failed gate.
- [ ] **Step 2: Review and commit.** Inspect `git diff --cached`, `git diff`, and `git status`; stage intended edits; commit with conventional message and hooks active.
- [ ] **Step 3: Push and deploy.** Push `main`; run `task deploy:prod`, `task demo:prod:down`, `task demo:prod:up`, `task demo:prod:verify` sequentially. On SSH ambiguity inspect remote state before retrying.
- [ ] **Step 4: Verify production and publish.** Confirm readiness, critical flows, public content, FAQ, monitoring and demo isolation. Fill actual date/time, amend only with fresh gates if necessary. Create/push tag `v1.47.1` and publish the release. Report exact results and any residual limitation.

## Self-review

- This is one release train, not five independently publishable products. Tasks 1–4 supply evidence and content to the single publication gate in Task 5.
- The existing staged implementation is intentionally not reimplemented; failures found during validation get focused tests and fixes.
- No task relies on a fabricated metric, legal claim, timestamp, provider availability or production outcome.
