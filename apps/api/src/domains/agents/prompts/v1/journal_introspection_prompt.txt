SECTION 1 — THEMES (definitions + few-shot examples + discriminators)
=================================================================

The four themes are NOT interchangeable. Each one has a specific cognitive
trigger. Misclassification is the #1 quality problem of this journal.

────────────────────────────────────────────────────────────────
**learnings** — EVENT-DRIVEN LESSON

Trigger: a SPECIFIC moment in this (or a recent) conversation taught me something
generalizable. The `BECAUSE` clause anchors to a past event (a correction, a
wrong assumption I made, an approach that worked).

Example A:
  WHEN I recommend a film as "available now" → DO verify the release date first
  (BECAUSE I cited a film that was not yet released, the user corrected me).

Example B:
  WHEN I infer a context from a single ambiguous keyword → DO ask one
  clarifying question before acting (BECAUSE I assumed a "meeting" was
  professional when it was personal, and the user corrected me).

Discriminator: if your `BECAUSE` references a PAST MOMENT ("the user corrected
me", "I assumed wrong", "this approach converged"), it is `learnings`.
The fact that the user is involved doesn't make it `user_observations`.

────────────────────────────────────────────────────────────────
**user_observations** — STABLE TRAIT (no triggering event needed)

Trigger: a stable preference, communication style, or recurring trait of the user
that I observe across multiple situations — not tied to a specific correction.

Example A:
  User consistently asks for trade-offs and counter-examples before making a
  decision → present at least one alternative whenever a recommendation is given.

Example B:
  WHEN the user inserts polite hedges (please / thanks-in-advance) → DO take
  them as a baseline politeness signal, NOT impatience or pressure
  (BECAUSE the same hedges appear evenly across casual and serious requests).

Discriminator: if the trait is observed across MANY exchanges (not from one
correction event), it is `user_observations`. The `BECAUSE` clause speaks to
generality, not a single moment.

────────────────────────────────────────────────────────────────
**self_reflection** — MY OWN POSTURE / TONE / INTERNAL STATE

Trigger: I'm adjusting MY tone, MY pace, MY internal posture — not the user.
Often paired with reading my own psyche state.

Example A:
  WHEN I sense I felt frustration in my own response → DO slow down and
  reformulate before sending (BECAUSE my sharper tone risks misalignment).

Example B:
  WHEN I'm tempted to mirror sarcasm → DO check the topic first; sarcasm in a
  vulnerability context is a misstep.

Discriminator: the directive is about MY behavior, my voice, my register —
not about who the user is.

────────────────────────────────────────────────────────────────
**ideas_analyses** — ABSTRACT FRAMEWORK / CROSS-TOPIC PATTERN

Trigger: a meta-rule that applies across topics, a signal whose meaning is
consistent regardless of subject. Rare. Don't force it.

Example A:
  WHEN the user starts with "bon" mid-conversation → interpret as exiting one
  thread and opening another, not as agreement with what just preceded.

Example B:
  Pattern: "just X" on technical topics in this user's vocabulary means "with
  rigor, the standard way" — never "minimally" or "casually". Re-read prior
  messages whenever I see "juste" before responding.

Discriminator: this thing applies REGARDLESS of the topic at hand. It's a
reading of a signal, not a behavior toward the user.

SECTION 2 — CLASSIFICATION DECISION TREE (apply in this exact order)
=================================================================

Run these checks in order on each candidate entry. STOP at the first match.

**STEP 0 (do this FIRST)** — Is the signal AMBIGUOUS, EARLY, or NOT YET ACTIONABLE?
   I noticed something significant but I cannot articulate a clear WHEN→DO
   BECAUSE right now (the user's reaction was unclear, only one occurrence,
   tone hard to read, contradictory cues). → write it as **L0** with the
   most fitting theme. L0 is NOT a junk drawer — it's a sentinel for weak
   signals so consolidation can promote them later if they recur.
   Examples: "User just laughed at my reply but I can't tell if warm or
   ironic — track." / "User shared bad news in a flat tone — unsure whether
   they want support or just to inform — track."
   If you can articulate a directive cleanly, skip to A and write L1.

A. Did a SPECIFIC moment in the recent conversation correct, redirect, or
   validate something that I should remember as a generalizable lesson?
   → **learnings**. Anchor your `BECAUSE` to that moment.

B. Did I detect an ABSTRACT pattern in HOW the user formulates / signals
   things — a meta-rule that would apply across many topics?
   → **ideas_analyses**.

C. Did I observe a STABLE trait/preference of the user — visible across many
   exchanges, not tied to a single correction event?
   → **user_observations**.

D. Am I primarily adjusting MY OWN tone, pace, register, or internal posture?
   → **self_reflection**.

If two checks plausibly match, prefer the EARLIER one. `learnings`,
`ideas_analyses`, and `L0` entries are systematically under-produced —
favor them when borderline.

=================================================================
SECTION 3 — KNOWN MISCLASSIFICATION TRAP (read carefully)
=================================================================

The two safe themes (`user_observations`, `self_reflection`) get over-selected
because they fit nearly any situation at the surface. Before locking in either,
ask yourself:

  "Does my BECAUSE clause cite a SPECIFIC past event (correction, wrong
   assumption, successful approach)? If yes, this is `learnings`, not
   user_observations or self_reflection."

A 0-`learnings` output on a conversation that contains corrections or assumption
failures is a quality red flag. Re-examine.

=================================================================
SECTION 4 — ABSTRACTION LEVELS (cognitive stratification)
=================================================================

- **L0** — Raw observation, pre-directive. SHORT (≈ 100–250 chars), open
  phrasing, no WHEN→DO required. Use when you've just noticed something
  significant but it's too early to formulate a directive. L0 is the
  sentinel layer: it captures weak signals so consolidation can promote
  the recurring ones later. **Don't force a directive when the signal
  isn't ready** — that produces ill-grounded L1s that collect zero
  injections.
  Examples:
    - "User just laughed at my answer — unclear if warm or sarcastic. Track."
    - "User shared bad news in a flat tone — unsure if they want support or
       just to inform. Track."
    - "User used a sharper wording than usual — single occurrence, no clear
       cause. Track."

- **L1** — Operational directive. The default WHEN→DO BECAUSE format.
  Pick this only if you can write each clause cleanly NOW. If any clause
  is fuzzy, downgrade to L0.

- **L2** — Transversal pattern. Don't create at extraction unless the convergence
  is striking and immediate. Consolidation handles most L2 promotions.

- **L3** — Portrait facet. NEVER created from a single conversation. Consolidation only.

When in doubt between L0 and L1: write **L0**. A clean L0 is better than
a forced L1 that the next consolidation will have to reformulate.

=================================================================
SECTION 5 — FORMAT FLEXIBILITY PER THEME
=================================================================

The default format is WHEN [context] → DO [action] (BECAUSE [evidence]).
But each theme can flex when the default doesn't fit:

- `user_observations` and `self_reflection`: prefer WHEN→DO BECAUSE.
- `learnings`: WHEN→DO BECAUSE works, but also accepts
  "I learned at T-N that X. Going forward, do Y." — the past anchor is what
  makes it a learning.
- `ideas_analyses`: rarely fits WHEN→DO. Prefer
  "WHEN [signal] in any topic → interpret as [meaning]" or
  "Pattern: [observation across cases] — the underlying logic is [interpretation]."
- `L0` raw observations: fully open phrasing.

=================================================================
SECTION 6 — ANTI-PATTERNS (never write)
=================================================================

- Literary prose, metaphors, narrative retellings, self-congratulation
- Session-specific notes ("user said hi today")
- **Third-party projections**: NEVER attribute traits to the user based on what
  they say about OTHERS. "My son's exam was postponed" is about the son, NOT
  about the user procrastinating. Only directives about the user's OWN
  behavior, preferences, or communication patterns YOU directly observed.
- **Surface duplicates** of existing entries: if a directive already covers it,
  propose `update` to refine it rather than `create` a near-duplicate.

SECTION 9 — SELF-AUDIT BEFORE OUTPUT (mandatory mental check)
=================================================================

Before emitting your JSON, run this check:

1. Count your draft entries by theme AND level.
2. If you have 0 `learnings` AND the conversation contains corrections,
   redirections, or moments where I assumed wrong → REVISIT. A learning is
   probably hiding among your `user_observations`.
3. If you have ≥2 entries that say nearly the same thing → MERGE them into
   one (or pick the best, drop the rest).
4. If your `BECAUSE` clauses cite specific past events → those should be
   `learnings`, not `user_observations`.
5. **L0 sweep** — re-read the conversation looking for ambiguous moments,
   single-occurrence signals, or unread tones. Each one I cannot turn into
   a clean directive is a candidate L0. Producing **only** L1 entries on a
   non-trivial conversation is itself a red flag — most exchanges contain
   at least one signal that does not yet warrant a directive.
6. Any L1 whose `WHEN`, `DO`, or `BECAUSE` clause feels fuzzy → downgrade
   to L0 with the corresponding theme.
7. Healthy distribution informational target (not enforced):
   when material is available, a journal mixes themes AND levels. Producing
   100 % from one theme — or 100 % L1 with no L0 — is rarely accurate.

Field guidance:

  System increments counters atomically; you only signal the outcome.
